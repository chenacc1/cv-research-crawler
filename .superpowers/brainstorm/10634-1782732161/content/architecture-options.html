Three Architecture Approaches

Trade-offs across simplicity, scalability, and development speed

Approach A — Monolithic All-in-One

A: Single Python Process
Scheduler
(APScheduler)
Crawlers
(arxiv/GitHub)
Report Gen
(Markdown)
Web Server
(FastAPI)
SQLite

Pros

  • 最快搭建，一个进程搞定
  • 部署简单，一条命令启动
  • 调试方便

Cons

  • 爬虫故障可能拖垮 Web
  • 扩展困难，耦合度高
  • SQLite 不适合高并发

Approach B — Heavyweight Microservices

B: Full Microservice Architecture
API Gateway
Auth Service
Arxiv Worker
GitHub Worker
Paper Worker
Report Worker
Redis
PostgreSQL
Message Queue

Pros

  • 高可扩展，各模块独立部署
  • 故障隔离好
  • 生产级可靠性

Cons

  • 过度设计，开发周期长
  • 运维成本高（Redis/MQ/多容器）
  • 个人使用场景杀鸡用牛刀

Approach C — Modular Monolith (Recommended)

C: Modular Monolith with Clean Boundaries
React Frontend → REST API
FastAPI Backend
Scheduler
Crawler
Registry
Report
Engine
SQLite (local)
⇄ PostgreSQL (server)
APScheduler
(in-process)

Pros

  • 模块边界清晰，爬虫/API/报告各自独立文件
  • SQLite 本地零配置 → PostgreSQL 一行配置切换
  • 后续按需拆分微服务容易
  • Docker 一键部署

Cons

  • 仍是单进程，大量爬取任务会阻塞
  • 无消息队列做任务削峰
  • 对个人使用足够，但不适合团队协作
